# 채팅 전환 지연 반감 연구

2026-10-30(KST)에 사용자의 명시적 지시로 두 번째 연구를 재개했다. **지연 반감은 아직 입증하지 못했으며 현재 연구를 진행 중이다.** 사용자는 주간 한도 증액을 알렸고, 감시기의 강제 조회에서도 사용률 40%를 확인했다. 이전 중단 상태와 실패 기록을 보존한 뒤 감시기를 새로 시작했으며, 이번에도 80% 이상에서 모든 Codex 하위 작업을 중단한다. 목표를 먼저 달성하면 불필요하게 한도까지 사용하지 않는다.

C1 후보와 원본 설치 상태는 그대로다. 먼저 정상 부팅 조회 계약을 보완하고 비점수 선택자 통계를 확보한다. 통계를 얻기 전에는 새로운 성능 성공이나 제품 채택을 주장하지 않는다. 하위 스레드에는 사용자가 허용한 Sol 모델도 사용한다. 아래 한도 종료 기록은 첫 차수의 상태이며 이번 재개와 구분한다.

## 두 번째 차수의 비점수 수집 상태

재개 후 세 수집은 모두 읽기 경계에서 중단됐으며 context 검증과 trace는 생성되지 않았다. 따라서 각 시도의 Agentation 기여 부재와 선택자 통계는 판정하지 못한다. 실패 뒤 자동 재시도하지 않고 별도 원본을 보존했다.

첫 시도는 navigation 단계의 미분류 GET에서 중단했다. 경로 segment 수는 4개였지만 실제 주소는 저장하지 않았으므로 해당 경로를 소급해서 특정할 수 없다. 결과 SHA-256은 `9a6c60dfeabf1797904776e5bf1802ae91cc67ead20f03d6a0643dd175f54181`다.

두 번째 시도는 허용 범위를 바꾸지 않은 채 고정 소스 ID만 거부 기록에 추가했다. 이번 거부는 공개 GET 등록 근거가 있는 `R_5925f8011e305e2d7498`로 분류됐으며, 기존 플러그인 갱신 작업의 목록 조회 형태였다. 이 분류는 첫 시도의 경로를 증명하지 않는다. 결과 SHA-256은 `3c3f7562ed46e7322f0e49f2d9756f984b21ee541b34bbec83a00a1c96d55ff3`다.

고정 소스에서 해당 조회는 기존 목록 반환과 만료된 완료 항목의 메모리 정리만 수행하며, 직접 호출 경로에 갱신 시작·외부 요청·파일/DB 쓰기가 없음을 확인했다. 정확한 GET 한 개만 추가한 세 번째 시도도 `read_path`에서 중단했다. 이번에는 거부 상세가 null이므로 원인 경로나 WebSocket 문제로 단정할 수 없다. 결과 SHA-256은 `b710206c43492c04328b356269e2dc37ba6113f12e5abe730c563192947c035c`다. 다음 준비는 이 중단 분기의 기록 누락을 오프라인으로 확인하는 작업이다.

각 시도는 합성 업데이트 응답을 한 번 사용했다. 서버 전달 0은 해당 실행기 분기의 기록이며 실제 업데이트 상태나 독립 서버 관측을 뜻하지 않는다. 서버 전후 snapshot은 일치했고 소유 Chrome과 실행기 종료를 확인했다. 측정자는 세 번째 시도 전부터 있던 사용자 Chrome의 개별 identity가 유지됐고 새 잔존 Chrome이 없었다고 사후 확인했다. 새로운 시간 점수나 제품 성공을 주장하지 않는다.

## 첫 차수의 한도 종료 기록

2026-10-29~30(KST)의 한도 종료 기록이다. **기능을 보존한 제품 후보의 지연 반감 목표는 달성하지 못했다.** 주간 사용률 80% 이상을 관찰한 뒤 새 실험과 하위 작업을 중단했으며, 부모는 최종 보고와 PR만 마무리했다.

감시기는 Codex 후손 18개의 중단 완료 응답을 기록했고, 후속 목록에서 진행 중인 Codex 후손은 없었다. 별도의 native 에이전트도 모두 완료 상태였다. 소유 실험의 Chrome·Node 프로세스가 남아 있지 않은 것을 확인했다. 호스트의 기존 상주 서비스는 종료하지 않았다. 첫 차수의 중단 latch 기록은 보존한다. 이 운영상 종료는 성능 목표의 성공 판정과 다르다.

## 사용자가 얻으려는 변화

채팅을 바꿀 때 Chat UI가 더하는 지연을 현재의 절반 이하로 줄이는 것이 목표다. 프로스트 외형과 기존 입력·정보 표시 동작을 유지한다. 자체 컴포저는 별도 구조 대안이며, 교체 가능성과 성능 향상은 다른 주장으로 다룬다.

연구 시작 조건으로 agentation을 실제 비활성화했다. 모든 새 측정은 이 조건의 새 브라우저에서 실행했다. 메인 체크아웃과 설치된 Chat UI는 원본을 유지한다. 후보는 별도 소스 사본에서 빌드하고 해당 브라우저 context의 자산 응답만 대체한다.

Codex 주간 사용률 감시 스크립트는 별도 프로세스로 실행한다. 80% 이상을 관찰하면 새 실험을 허용하지 않고, 부모를 제외한 Codex 후손의 중단 요청을 시작한다. 부모는 결과 보고와 PR 작성만 계속한다. 사용률은 계정의 주간 한도 비율이며 토큰 개수 자체가 아니다. 원시 계정 응답과 로컬 상태는 저장소에 넣지 않는다.

## 기준과 재현 범위

### 시작 시점과 BB의 변화

확인 가능한 Git ref의 최초 커밋은 2026-10-03 15:32:18 KST의 [`0b718ef`](https://github.com/MORPHLET/bb-chat-ui/commit/0b718ef153a052b9340b880dc2654fc92edd197e)이며 빈 등록 골격이었다. 최초 실제 화면은 같은 날 16:11:46 KST의 [`fdf5fea`](https://github.com/MORPHLET/bb-chat-ui/commit/fdf5fea1748c9b0b3b8d734d41da9b7ae46f1208)에서 변경 요약 pill과 Diff 열기를 추가했다. 당시 package의 BB `>=0.44`는 최소 호환 조건이다. 시작 당시 실제 설치판은 확인하지 못했다. 당시 이미 공개된 안정판은 [0.45.0](https://github.com/get-bb/bb/releases/tag/desktop-v0.45.0)이었다. 현재 CLI와 서버의 0.48.0은 별도로 확인했으며 공식 비교 근거는 [0.48.0 릴리스](https://github.com/get-bb/bb/releases/tag/desktop-v0.48.0)와 그 태그의 [고정 CHANGELOG](https://github.com/get-bb/bb/blob/1a4a1d254c7b1f70d340ef9c800dad77dbeb8e66/CHANGELOG.md)다.

공식 기록상 0.46은 메시지 링크, 승인 표시, 큐 편집 보호, Info 개편과 상세 지연 로드를 추가했다. 0.46.1은 모바일 큐와 스크롤 보정 및 code-fence renderer를 다뤘다. 0.47은 메시지 편집과 읽기 위치, 모바일 패널 swipe, 통합 탭 계약을 확장했다. 0.48은 하단 고정과 큐 순서, 열린 패널 우선 로드, 변경분 전송과 패널 너비 기억을 다뤘다. 이는 공개된 동작과 개선 발표이며 이번 머신의 속도 측정 결과는 아니다. 메시지 액션과 실험적 timeline windowing은 시작 전에도 있었으므로 0.48의 신기능으로 계산하지 않는다.

### 유지·단순화·대체의 경계

호스트는 메시지 렌더링·편집·첨부·스크롤·큐·승인과 탭 수명을 관리한다. Chat UI는 frost, compact 인용, 정보 pill·상세 카드, 목차 미리보기, phone 시트와 모션을 추가한다. 이 제품 동작은 유지하고 불필요한 전역 처리부터 줄인다. 본문·코드·표와 첨부의 표면은 스타일 단순화 후보이며, 공개 메시지 액션은 새 액션을 추가할 때 우선 검토할 수 있다. 다만 메시지 전체 교체 계약은 아니다. [공식 SDK 계약](https://github.com/get-bb/bb/blob/1a4a1d254c7b1f70d340ef9c800dad77dbeb8e66/packages/plugin-sdk/src/app-contract.ts)과 [ThreadChat 공개 진입점](https://github.com/get-bb/bb/blob/1a4a1d254c7b1f70d340ef9c800dad77dbeb8e66/packages/plugin-sdk/src/app.ts)을 기준으로 범위를 구분했다.

설치 목록에서 inline-vis·genui는 메시지 시각화, image-preview는 이미지 미리보기, message-date-time은 시각 표시를 제공한다. Drafts·예약 전송·Secrets·질문 기능은 호스트가 제공하는 동작과 연결된다. panel-tabs와 호스트의 탭 관리도 겹치는 영역이다. 목록의 활성 상태만으로 실제 표시나 중복 비용을 입증하지 않는다. 시각화 iframe을 숨기는 것만으로 내부 실행이 멈춘다는 보장도 없다.

Git과 PR은 각각 [번들 Git](https://github.com/get-bb/bb/blob/1a4a1d254c7b1f70d340ef9c800dad77dbeb8e66/plugins/git/app.tsx)과 [GitHub PR Status](https://github.com/get-bb/bb/blob/1a4a1d254c7b1f70d340ef9c800dad77dbeb8e66/plugins/github-pr-status/store.ts)가 제공한다. PR 서버에는 캐시와 진행 중 요청 공유가 있어 중복 RPC 감소를 같은 비율의 서버 작업 감소로 계산하지 않는다. 자식 목록과 Git 조회의 생략은 공개 이벤트에 충분한 변경 정보가 없어 보류했다. 통합 패널 API는 [호출 플러그인의 소유권을 검사](https://github.com/get-bb/bb/blob/1a4a1d254c7b1f70d340ef9c800dad77dbeb8e66/apps/app/src/lib/plugin-panel-controller.ts)하므로 다른 플러그인의 Diff 탭을 공개 API로 직접 열 수 있다고 가정하지 않는다.

### 이번 실험 환경

제품 소스는 `50ba38154180331583eca024aaac0612a1d85a50`, CLI·서버는 BB 0.48.0이다. Windows의 Chrome 156.0.8078.48 headless에서 실제 사이드바로 두 완료 연구 스레드를 왕복한다. desktop device,1100×750,새 context,고정 warmup과 순서를 사용한다. 사용자 메시지·초안·설정·탭 상태를 쓰지 않는다. 탭 갱신은 context별 메모리 overlay로 처리하며 실제 서버의 시작·종료 snapshot 일치를 확인한다. 이 overlay는 서버 DB 지연과 broadcast를 재현하지 않는다.

원본 JavaScript SHA-256은 `b48976d46ee1a4e481be935db567b0353f93d7e8e54fa05d9bb51f2d663dbc04`다. 원본 CSS는 `bf26fb81381afa72c8c516b2c44b7b34153a66cbf8520a3b211d73ca4277e15d`다. BB는 이미 호스트가 제공하는 Tailwind 항목을 제외한 CSS를 브라우저에 전달한다. 이 환경의 전달 CSS는 `0af2fca3bf63d1bf2836bebdb65c29665be6bc7b8e6f0c13eb2b260a4253fa17`다. 검사는 원본 해시 고정과 같은 요청의 직접 서버 응답·브라우저 응답 바이트 일치를 각각 확인한다.

일차 지표는 실제 클릭 캡처부터 대상 스레드의 고유 행을 DOM에서 찾고 표시·viewport 교차·hit-test를 확인한 시점까지다. 60ms polling과 자동화 작업이 포함된다. **실제 paint, INP 또는 입력 반응 완료 시간을 직접 재지 않았다.** 이후의 focus 확인은 별도 관측이다. Electron 사용자 창, 실물 phone, 실제 IME·voice, 사용자의 시각 판정도 아직 확인하지 않았다.

A1/A2는 같은 원본을 새 context에서 각각 실행한다. N은 JS entry만 no-op으로 바꾸고 metadata와 CSS URL을 남긴다. URL 존재와 실제 stylesheet 적용은 구분한다. F는 해당 context의 plugin 목록에서 Chat UI 항목만 제외해 JS·CSS와 표시 기여를 로드하지 않는다. F도 backend는 유지하므로 전체 플러그인을 전역 비활성화한 조건이나 모든 native BB 사용을 뜻하지 않는다.

## 완료한 기준선 탐색

독립 Chrome 실행 4개 안에서 각각 A1/A2/N/F를 순차 실행했다. 각 context는 warmup 2회 뒤 관측 6회를 수행했다. 16개 context가 자산·metadata·대상 행·focus·오류·overlay 검사를 통과했다. agentation의 자산·toolbar·freeze hook과 rAF 변경은 없었고, Chrome을 모두 종료했으며 서버 탭 상태는 전후 일치했다.

각 블록의 원본 두 중앙값 평균에서 F 중앙값을 뺀 차이는 428.5,248.9,272.8,250.1ms였다. 같은 코드 A1−A2도 238.7,49.3,65.5,−13.4ms 차이를 보였다. 후자를 무시하고 전환 관측 96개를 독립 표본으로 세지 않는다. 값은 [정리된 관측 자료](chat-switch-discovery.json)에 보존했다. 독립 검토자는 원시 시각에서 요약을 재계산했다. 후보는 이 단계에서 측정하지 않았다.

첫 기준 실행은 CSS 해시 gate에서 중단했다. 브라우저 전달 CSS 변환을 검증하지 않은 검사 오류였다. 해당 실패는 보존하고, 고정 BB 소스의 변환 경로와 같은 요청의 바이트 관계를 확인한 뒤 별도 run-02로 전체를 실행했다. 실패 값을 원본 허용 목록에 단순 추가하지 않았다.

## 원인 분리와 다음 후보

정보 표시와 프로스트 각각에 대해 controller 없이 스타일만 유지하거나 스타일 없이 controller만 유지하는 네 변형을 빌드했다. 외부 app.css는 원본과 같았다. 원본과 F를 포함한 6조건을 독립 Chrome 블록 3개,18개 context에서 비교했다. 모든 검사와 독립 재계산을 통과했다.

정보 controller만 유지하고 해당 주입 스타일을 제외한 조건은 원본보다 세 블록 모두 낮았다. 원본 중앙값은 530.1/535.2/486.9ms, 해당 조건은 315.4/335.4/369.7ms였다. 그러나 외형·배치·스타일 일치 여부가 달라졌으므로 이 차이는 순수 CSS 비용이나 출하 가능한 개선량이 아니다.

다음 진단 H는 Workflow의 agent 행 규칙 네 개와 CircleCheck 조건 두 가지만 제외했다. 세 블록의 원본/H/F 중앙값은 각각 533.5/373.6/264.3ms, 510.3/346.8/228.4ms, 544.8/411.3/223.6ms였다. H는 원본보다 159.9/163.5/133.5ms 낮았다. 모든 context 검증과 독립 재계산이 통과했다. 그러나 측정 전후에는 Workflow trigger가 없었고, 중간 상태까지 증명한 것은 아니다. 열린 화면을 바꿀 수 있는 기능 제거 진단이므로 이 수치를 제품 후보의 개선량이나 순수 선택자 비용으로 사용하지 않는다.

인용 pill의 별도 후보는 같은 MutationObserver 콜백에서 추가되는 인용의 위치 계산을 동기로 모은다. 가짜 데이터의 비점수 브라우저 검증에서 기존 인용 1개와 새 인용 3개는 좌표 읽기가9회에서4회로 줄었다. 첫·후속 크기 변경 후 위치와 콜백 반환 전 위치를 확인했다. ResizeObserver는 유지한다. 이 결과는 실제 전환의 사용 빈도나 시간 효과를 증명하지 않는다. 첫 진단의 RO 검사 실패와 기존 M2 효과 기준 미충족도 유지한다.

## 외형을 보존하는 C1 후보

검증한 후보 커밋은 `d9af383ab2f571a926e02a22204a0c02c3fc1fa5`다. 닫힌 Workflow 상세 카드에만 필요한 연속 스타일 구간을 분리하고, 첫 열기에서 표시와 위치 측정 전에 연결한다. 여러 카드가 열리면 마지막 카드가 닫힐 때 분리한다. 편집 중 닫기가 거부되면 연결을 유지한다. 공통 카드 규격과 인용 스타일은 계속 연결한다. 열린 상태의 전체 정보 CSS 텍스트는 원본과 바이트 단위로 같고 적용 순서를 보존한다. 이는 H의 단순 삭제보다 기능을 보존하려는 후보이며 효과는 별도로 측정해야 한다.

후보의 focused 검사, 타입 검사, 빌드와 전체 테스트 694개가 통과했다. 최초 전체 실행은 기존 검수 helper가 분리된 스타일의 뒷부분을 읽지 못해 실패했다. 연결된 정보 스타일을 DOM 순서대로 읽도록 helper를 고쳤고 기존 검증 조건은 유지했다. 별도 사본에서 마지막 카드 소유자 판정을 반대로 바꾼 변이는 다중 카드 검사에서 실패했다.

독립 데모 QA는 기준·후보 각각 desktop/phone 모사와 light/dark의 총 8개 context를 검사했다. 열기·닫기·다중 카드·편집 중 닫기 거부·정리, 활성 CSSOM 규칙과 순서, 첫 표본 프레임이 일치했다. 입장 모션 중 서로 다른 시점에 비교한 앞선 프레임 검사는 실패했다. 그 기록을 보존하고 모션 완료 후 같은 동작을 시작하는 조건에서 기존 2px 경계를 유지해 다시 검사했다. 첫 표본 프레임은 첫 paint와 다르다. 데모는 같은 제품 TS 소스 사본을 변환해 가짜 데이터를 주입했으며 설치된 app.js 실행이나 실제 BB 통합을 증명하지 않는다. 캡처는 desktop·phone 모사에 있고 실물 phone 캡처는 없다. 화면의 최종 판정은 사용자에게 남는다.

실제 BB의 비점수 사전 검사에서는 원본과 후보에 보이는 대화 행이 두 대상에서 각각 5개와 3개로 일치했다. 정규화한 정보 데이터, 모델·환경 표시, 새 context의 초안·첨부 비교도 일치했다. 비교 내용은 메모리에서만 처리하고 원문과 내용 해시는 보존하지 않았다. Agentation 비활성, 자산·CSS·서버 상태 검사와 종료 확인도 통과했다. 이는 표시된 일부 행과 새 context의 상태에 한정된다. 화면 밖 행, 실제 사용자 창의 초안, 전체 렌더러 입력 또는 서버 GET의 직접 소비는 증명하지 않는다. 이 검사에는 읽기 전용 계측 번들을 썼으며 시간 측정에는 무수정 제품 번들을 사용한다.

사전 검사의 첫 실행은 프로토콜에 복사한 CSS 해시 두 개가 각각 65자라서 중단됐다. 실패를 보존하고 원본과 QA JSON에서 정상 64자 값을 기계적으로 가져오도록 고쳤다. 해시 형식, QA·커밋·실제로 전달할 번들 사이의 연결도 검사한다. 두 번째 실행이 통과했으며 첫 실행을 통과로 변경하지 않았다. 스타일의 첫 연결 비용이 첫 열기에 옮겨갈 가능성도 별도 검증 대상으로 남는다.

### 비점수 긴 프레임 관찰

원본과 C1에서 각각 새 context 하나, warmup 2회 뒤 전환 4회를 짧게 관찰했다. 전환 구간과 겹친 LoAF는 원본 11개, C1 4개였고 script 기록은 각각 26건과 21건이었다. 보고된 누락 수는 0이지만 완전 수집을 증명하지 않는다. 이 관찰은 지연 점수 실험과 분리했으며, 단일 context의 프레임 수 차이로 성공이나 인과관계를 판정하지 않는다.

원본과 C1 모두 정보 표시, 프로스트, viewport 처리의 진입 위치가 있었다. 각 source map이 관찰된 JS와 바이트가 같은지 확인한 뒤 C1의 숫자 위치를 `composer-info.ts:2561:11`, `composer-glass.ts:932:43`, `composer-viewport.ts:50:47`로 분류했다. 진입 위치는 강제 layout을 유발한 getter나 앞선 invalidating write를 식별하지 않는다. 전체 script·forced 시간에는 전환 구간 밖 부분과 서로 겹치는 구간이 있어 순수 플러그인 비용으로 합산하지 않는다. `host` 분류도 알려진 plugin asset 외의 같은 origin을 뜻하므로 모두 BB 앱 코드라고 부르지 않는다. 메시지·DOM 원문, URL, 함수명과 사용자 내용은 저장하지 않았다.

### 전역 stylesheet 그룹의 제어 확인

직접 CSS import는 공용 모션 파일이지만, BB 빌드는 theme과 범위가 제한된 Tailwind utility도 합친다. 실제 산출물에는 Tailwind preflight의 `@layer base`가 없었다. 외부 CSS 크기만 보고 전역 reset을 중복 적용한다고 가정하지 않는다. 외부 CSS를 끄면 모션·reduced-motion과 일부 bridge typography도 영향을 받을 수 있으므로 이 역시 제품 동등 후보가 아니다.

동일한 C1 JavaScript와 네트워크 응답을 유지하면서 실제 `CSSStyleSheet.disabled`만 바꾸는 방법을 비점수 사전 검사했다. 합성 페이지에서 link와 style의 적용·비활성 및 계산 스타일을 확인했다. 실제 문서에서는 info prefix/tail 전체 제외(IN)가 대상 하나의 표시 행·개수 비교에 실패했다. 나머지 입력과 stylesheet 제어는 맞았으나 원인은 확정하지 못했다. 이 조건을 시간 비교에서 제외하고 실패를 보존했다.

별도 사전 검사에서 원형 C1, 외부 CSS만 비활성(EX), info 외의 확인된 명명 style 그룹만 비활성(OT)이 양 대상 입력·스타일·안전 검사를 통과했다. 높이·스크롤을 담당하는 익명 viewport style은 활성 상태로 유지했다. 조건부 phone 확장 스타일도 이 desktop 그룹에 포함하지 않았다. 전체 renderer 입력이나 화면 외형의 동등성을 뜻하지 않으며 이 단계에서는 시간값을 수집하지 않았다. 이 세 조건만 별도 순서 균형 탐색으로 비교한다.

### 프로스트 스타일과 나머지 스타일의 분리

OT의 11개 스타일을 composer-glass 한 개(GS)와 나머지 열 개(RS)로 나눴다. GS는 프로스트 스타일만 비활성화하고, RS는 그 스타일을 유지하며 나머지를 비활성화한다. OT는 두 그룹을 모두 비활성화한다. 정보 스타일, 익명 viewport 스타일, 외부 CSS와 JavaScript는 유지했다. 네 조건의 비점수 사전 검증 뒤, 독립 Chrome 블록 네 개에서 위치를 회전해 비교했다.

16개 context의 스타일·입력·자산·Agentation·사용량·서버 상태 검사는 통과했다. 독립 검토자가 중앙값과 방향별 값, 조건 간 차이를 원시 시각에서 다시 계산했다. GS는 네 블록에서 모두 낮았지만 차이의 크기는 일정하지 않았다. RS와의 차이는 가산적이지 않으며, 이 결과는 특정 선택자나 frost 효과의 순수 비용을 입증하지 않는다. 프로스트를 제거한 상태는 제품 후보로 채택하지 않는다.

멘션 메뉴를 판별하는 세 규칙만 제거한 MH와, 같은 세 규칙의 class 속성 조건을 이스케이프한 class 선택자로 바꾼 CL을 비교했다. 정적 생성물은 CL의 class token과 specificity가 같음을 확인했다. 비점수 브라우저 검사에서는 실제 번들의 주입 CSS, 합성 CSSOM의 세 규칙과 선언 순서, 128개 매칭·계산 스타일 사례 및 경쟁 선언 여덟 개를 대조했다. 실제 연구 대상의 메뉴 DOM 개수는 모두 0이었으므로 열린 native 메뉴와 전체 host CSS의 동등성은 확인하지 못했다.

첫 비점수 실행은 CSSOM 검사기의 style 규칙 분류에서 중단됐다. 해당 실패는 보존하고 이전 QA 판독기와 대조해 수정한 별도 실행만 통과 근거로 사용했다. 이후 네 조건을 네 독립 Chrome 블록에서 비교했다.

| 블록 | C1 | MH | CL | GS |
|---|---:|---:|---:|---:|
| 1 | 362.20ms | 400.20ms | 423.60ms | 343.70ms |
| 2 | 441.05ms | 412.15ms | 372.35ms | 396.55ms |
| 3 | 430.65ms | 427.60ms | 385.25ms | 397.80ms |
| 4 | 429.30ms | 397.05ms | 399.20ms | 366.80ms |

MH와 CL은 차이의 방향이 블록마다 달라 채택을 보류했다. GS는 이번에도 네 블록에서 낮았지만 프로스트 외형을 제거한 진단이므로 제품 후보로 채택하지 않는다. 16개 context의 유효성 검사와 독립 재계산은 통과했다. 다음 진단은 handoff 조건 한 개와 멘션 조건 세 개의 조합을 분리한다.

고정 Chromium 소스는 :has() 내부의 class selector를 class 토큰 집합에, 속성 selector를 속성 이름 집합에 수집하는 [별도 경로](https://chromium.googlesource.com/chromium/src/+/d4d257b3186bca0db8260fd5fd0303ca8b5a707d/third_party/blink/renderer/core/css/invalidation/rule_invalidation_data_visitor.cc#1116)를 갖는다. 이는 비교 가설의 코드 근거이며, 현재 Chrome 156과 같은 revision인지 또는 CL이 더 빠른지를 증명하지 않는다. 다른 활성 규칙과 후속 조건도 영향을 준다.

### Handoff와 멘션 조건의 조합

HF는 handoff 반경 조건 한 개만 제거하고, AH는 그 조건과 멘션 조건 세 개를 함께 제거한다. 실제 주입 glass CSS의 :has 규칙은 C1/HF/AH 순서로 4/3/0개였다. GS는 원본 네 규칙을 포함한 stylesheet를 비활성화한다. 비점수 네 context와 합성 16개 사례에서 삭제 범위·예상 기능 차이 및 실제 두 대상의 관측 입력을 확인했다. 연구 대상에는 메뉴와 handoff DOM이 모두 없었다.

| 블록 | C1 | HF | AH | GS |
|---|---:|---:|---:|---:|
| 1 | 385.10ms | 403.55ms | 344.80ms | 332.50ms |
| 2 | 411.60ms | 379.10ms | 395.75ms | 327.90ms |
| 3 | 415.35ms | 378.55ms | 364.65ms | 409.95ms |
| 4 | 422.85ms | 362.65ms | 399.65ms | 360.85ms |

16개 context 검사와 독립 재계산은 통과했다. AH와 GS는 네 블록에서 모두 낮았지만 HF는 차이 방향이 달랐다. 조건을 함께 제거했을 때의 결과이므로 개별 규칙의 순수 비용이나 합산 가능한 개선량으로 해석하지 않는다. 삭제안을 제품으로 적용하지 않고, 실제 상태를 컴포저에 직접 표시해 같은 선언을 선택하는 기능 보존 후보 GM을 별도로 준비한다. 새 observer와 조회 비용, 동적 상태·여러 컴포저·정리 및 첫 표본 프레임을 검증해야 하며 첫 paint나 native 동기 위치 읽기의 동등성은 별도 문제다.

### GM 기능 보존 후보의 닫힌 화면 탐색

GM은 네 조건 규칙을 실제 자손 상태에 따른 컴포저 표식 두 개로 대체한다. 기존 컴포저 관찰자를 재사용하고 class·aria-label과 자손 변경을 감시한다. 초기 설치는 동기이며 관련 관찰자 callback 반환 전 상태를 맞춘다. 원래 선언·순서·specificity와 frost 관련 선언은 바꾸지 않는다. 열린 상태의 시각 동등성은 별도로 검증해야 한다. 집중 테스트 63개와 타입 검사·빌드·생성 CSS 대조는 통과했다. 표식 누락과 갱신 지연 변이는 테스트에서 실패했다.

단, DOM 변경 직후 callback 실행 전에는 원본 :has와 스타일이 다를 수 있다. 이 차이를 동등성 통과로 계산하지 않는다. 열린 상태와 callback 전 동기 읽기의 검증이 끝나기 전에는 제품 채택 및 최종 반감 확인을 진행하지 않는다. 전체 테스트와 열린 상태 QA를 준비하는 동안, 메뉴·handoff가 없는 실제 두 대상의 닫힌 관측 범위만 별도 프로토콜로 확인했다. 당시 QA 상태는 pending으로 보존했다. 이후 동일 소스·번들에서 전체 테스트 696개가 모두 통과했고 실패·건너뜀은 없었다. 기존 manifest는 그대로 두고 테스트 전후 해시를 별도 증거에 연결했다. 이후 열린 상태 QA에서는 아래의 동기 모션 차이가 관찰됐다.

실제 번들의 비점수 네 context에서 컴포저별 표식과 native 자손 상태, 주입 CSS 및 입력·안전 검사가 통과했다. 다음 시간 탐색은 새 seed와 네 위치 회전을 사용했다. 다른 연구자는 측정 중 작업을 멈췄고 후보의 관찰자·조회 비용도 포함했다.

| 블록 | C1 | GM | GM−C1 |
|---|---:|---:|---:|
| 1 | 457.20ms | 402.05ms | -55.15ms |
| 2 | 445.70ms | 415.05ms | -30.65ms |
| 3 | 409.55ms | 395.25ms | -14.30ms |
| 4 | 416.60ms | 360.55ms | -56.05ms |

16개 context 검사와 독립 재계산은 통과했고 소유 브라우저·실행기 종료를 확인했다. 네 블록 모두 GM이 낮았지만 이번 비교에는 동시대 원본 O와 프런트엔드 제외 F가 없어 반감 목표를 판정하지 않는다. 후속 기능 검사에서 차이가 관찰돼 GM의 제품 채택과 O/GM/F 실행을 보류했다.

후속 QA는 검수 데모의 전역 변수 중복 선언과 favicon 요청, 특이도 계산기 호출 경로 및 미지원 컨테이너 CSSOM 판독을 차례로 분리했다. 수정과 실패 기록을 각각 보존했다. 진행 중이던 초기 transition의 미세한 표본 시간 차이도 관찰해, 초기 프레임 검사는 유지하면서 동적 조작 전에 기존 유한 모션의 자연 종료를 확인했다. 그 준비 조건의 별도 QA에서 일부 멘션 동작은 통과했지만 handoff 삽입의 동기 모션 검사에서 중단됐다.

독립적인 단일 handoff 대조에서 같은 C1 두 개는 sync·callback-after·first-frame 검사를 모두 통과했다. C1/GM은 동기 시점 A의 transition 개수가 4개와 0개로 달라 중단됐다. 이 시점의 고정 계산 스타일 값은 같았고, GM의 callback 이후 및 첫 frame은 실행하지 않았다. 이전 QA와 정확히 같은 실패 분기인지 또는 차이의 원인이 무엇인지는 확정하지 않는다. 같은 원본 대조와 달리 관측된 후보 차이가 있으므로 기준을 낮추지 않고 보류했다. 새 후보 GMM은 원래 handoff CSS와 동작을 유지하고 멘션 표식만 남기는 별도 사본으로 준비한다.

### 멘션 전용 GMM의 닫힌 화면 탐색

GMM은 원래 handoff CSS와 반경 처리 본문을 유지하고, 멘션 세 조건만 표식 하나로 바꾼 별도 사본이다. 닫힌 화면의 비점수 네 context에서 실제 주입 CSS와 컴포저별 표식·자손 상태 및 양 대상의 관측 입력을 확인했다. C1/GMM/GM/MH의 실제 주입 :has 개수는 각각 4/1/0/1이었다. 열린 상태 QA와 전체 테스트는 아직 실행을 마치지 않았다.

새 seed와 네 위치 회전을 고정한 시간 탐색은 각 context에서 warmup 2회 뒤 관측 6회를 수행했다. 표식·조회 비용을 포함했고, 16개 context의 검사와 독립 재계산이 통과했다. Agentation 비활성, 서버 상태 일치와 소유 Chrome·실행기 종료도 확인했다.

| 블록 | C1 | GMM | GMM−C1 |
|---|---:|---:|---:|
| 1 | 453.55ms | 423.20ms | -30.35ms |
| 2 | 452.25ms | 395.35ms | -56.90ms |
| 3 | 418.15ms | 364.00ms | -54.15ms |
| 4 | 416.15ms | 439.10ms | 22.95ms |

세 블록은 낮았고 한 블록은 높았다. 이 탐색으로 개선의 안정성이나 반감 성공을 판정하지 않으며 현재 제품 변경으로 채택하지 않는다. 함께 비교한 GM은 이미 동기 handoff 차이가 확인된 참고 조건이고 MH는 기능 제거 조건이다. 전체 자료는 같은 두 연구 대상을 다시 사용했으며 O/F 동시 비교가 아니다. GMM의 열린 화면과 callback 전 동기 동작은 미검증으로 남긴다. 다음 작은 진단은 새 observer 대신 CSS 적용 범위를 좁히는 방법을 검토한다. 적용 순서와 scope proximity에 따른 외형 차이도 별도 검사해야 한다.

### CSS 범위 제한 SC 진단

SC는 C1의 네 glass 조건 규칙을 원래 위치의 두 @scope 블록으로 바꾸고 명시적 :scope를 사용한다. 선언·상대 순서·specificity와 나머지 CSS·JavaScript는 보존하며 새 관찰자를 추가하지 않는다. 고정 Chrome용 진단이며 미지원 엔진용 fallback은 구현하지 않았다. 실제 브라우저 사전 검증에서는 두 범위 블록과 네 규칙의 주입·활성 CSSOM을 확인했다.

제품 CSS만 쓰는 합성 상태 260개는 C1과 같았다. 같은 specificity의 경쟁 선언을 추가한 별도 검사 8개도 예상 판정을 만족했다. 이 검사에서는 scope proximity로 달라지는 반례를 확인했다. 따라서 이 결과는 범용 cascade 동등성이나 실제 열린 메뉴·전체 host CSS의 동등성을 증명하지 않는다. 기준 상태의 예상 밖 차이와 미지원은 실패 조건으로 유지했다.

| 블록 | C1 | SC | GS | SC−C1 |
|---|---:|---:|---:|---:|
| 1 | 411.40ms | 422.45ms | 370.65ms | 11.05ms |
| 2 | 439.00ms | 439.40ms | 360.10ms | 0.40ms |
| 3 | 418.95ms | 351.20ms | 380.65ms | -67.75ms |

아홉 context의 입력·주입 스타일·자산·Agentation·사용량·서버 상태 검사와 독립 재계산이 통과했고 소유 Chrome·실행기의 종료를 확인했다. 차이는 세 블록에서 같은 방향을 보이지 않아 SC를 제품 변경으로 채택하지 않는다. GS는 프로스트 스타일을 비활성화한 진단이므로 출하 후보가 아니다. 선택자 매칭의 순수 비용이나 반감 성공도 이 비교로 판정하지 않는다. 다음 조사는 비점수 선택자 통계로 실제 매칭 비용이 집중된 규칙을 확인하는 데 사용한다. 계측 자체의 큰 부하는 기존 시간 점수와 분리한다.

### 선택자 통계 수집의 선행 실패

실제로 매칭 작업이 집중되는 규칙을 찾기 위해 별도의 비점수 SelectorStats 수집을 준비했다. 계측 부하가 크므로 앞선 전환 시간과 비교하지 않으며, 검증된 스타일시트별 수집 구간 합계만 다룬다. 특정 frame·getter가 지연을 일으켰다는 인과관계로 해석하지 않는다.

첫 실행은 허용된 읽기 경로 검사에서 중단됐다. 차단된 실제 경로는 저장하지 않아 원인을 확정하지 못했다. context 검증과 trace가 없어 이 실행에서 Agentation 부재나 선택자 통계를 판정하지 않는다. 실행 중 기록은 Chrome 정리를 미확인으로 남겼고, 이후 OS 조회에서 실행기와 소유 Chrome의 부재를 확인했다. 사후 확인으로 원래 기록을 성공으로 바꾸지 않았다.

두 번째 실행은 Chrome 시작 전 자산 경로 검사에서 중단됐다. context 검증·trace·서버 snapshot을 생성하기 전 단계였으며, 실행기와 Chrome의 부재를 확인했다. 설치된 서버는 bundle hash를 포함하는 자산 경로를 만들지만 검사기는 이 형식을 허용하지 않는 정적 불일치를 발견했다. 실패 분기가 저장되지 않아 이것이 실제 중단 원인인지는 확정하지 못했다. 두 실패와 실행 당시 고정본은 별도로 보존한다.

경로 계약을 고친 세 번째 실행도 화면 이동 중 읽기 경로 검사에서 중단됐다. 기록은 GET·경로 구간 4개·미지 경로 분류에 한정되며 실제 경로는 알 수 없다. trace와 context 검증은 생성되지 않았고, 서버 전후 snapshot 일치와 소유 Chrome·실행기의 종료를 확인했다. 공개 서버 경로에 근거한 진단용 분류를 보강하되 네트워크 허용 범위는 넓히지 않는다.

분류만 보강한 네 번째 실행에서는 서버 이동 상태 조회의 공개 GET 형태가 차단된 것을 확인했다. 설치된 서버 코드에서 해당 handler는 이동 시작·취소나 설정 변경 없이 상태를 읽는다. 이 분류는 이전 실행의 요청을 소급해 특정하지 않는다. 이번에도 trace와 context 검증은 없으며, 서버 전후 snapshot과 프로세스 종료는 확인했다. 수집 전 검사에서 멈춘 실행을 선택자 통계나 성능 결과로 사용하지 않는다.

다섯 번째 실행은 앱 업데이트 상태 조회의 공개 GET 형태가 차단되어 중단됐다. trace와 context 검증은 생성되지 않았으며, 서버 전후 snapshot 일치와 소유 프로세스 종료를 확인했다. 이 handler는 조건에 따라 새 업데이트 확인을 시작할 수 있어 단순 캐시 읽기와 구분한다. 실제 다운로드·설치·설정 변경을 허용하는 근거로 사용하지 않는다.

현재 대상 서버의 설치 방식을 확정하지 못해 여섯 번째 실행에서는 업데이트 GET을 서버에 전달하지 않았다. 공개 응답 계약의 합성 `unsupported`·`idle` 고정 응답을 한 번 적용했다. 실행기 경계의 fulfilled 1·serverForwarded 0을 기록했으며 별도의 서버 관측은 아니다. 이 고정 응답은 실제 호스트 상태나 완전한 native 동작의 증거가 아니다.

이 실행도 기존 플러그인 설치 작업 목록 GET 형태가 차단되어 중단됐다. 설치된 서버 코드에서 해당 조회는 새 설치를 시작하지 않지만, 보존 기간이 지난 완료 항목을 메모리 목록에서 정리한다. trace와 context 검증은 없고 서버 snapshot과 프로세스 종료는 확인했다. 여섯 시도 모두 선택자 통계를 얻지 못했으며 이번 연구에서 추가 브라우저 재시도는 하지 않는다. 정상 부팅 조회의 계약을 실제 수집 전에 완성하지 못한 측정 준비의 한계로 기록한다.

초기 M2의 설치 구간 wall time만 재는 안은 후속 작업을 빼먹을 수 있어 철회했다. 고정 관찰 구간으로 바꿀 때도 등록 시작 뒤 500ms 전체가 포함되는지 확인했다. 이와 같은 측정 경계 수정은 이미 수집한 실패를 합격으로 바꾸는 근거가 아니다. 작은 fixture의 A/A 실패가 반복됐으므로 현재 연구는 실제 채팅 전환에 영향을 주는 전역 스타일로 초점을 옮겼다. 기존 후보는 새로운 실사용 빈도와 비용 근거가 생기면 다시 조사할 수 있다.

과거 한 블록의 진단값835.6ms와331.0ms에서 나온 절대 중간값583.3ms를 남긴다. 과거 실험은 프런트엔드 응답 대체였으므로 이번 실제 agentation 비활성 조건과 동일한 조작으로 부르지 않는다. 과거 절대값만 낮아졌다고 목표를 달성한 것으로 처리하지 않는다.

후보 C는 별도의 동시대 원본 A와 F를 함께 측정해야 한다. 초안은8개 독립 Chrome 블록에서 context 중앙값을 구하고,블록별 `D=C−(A+F)/2`와 `G=A−F`를 분석한다. D 평균의 단측97.5% t 상한이0이하이고 G 평균의 단측97.5% 하한이0보다 클 때만 공동95% 기준의 반감 근거로 다룬다. 이는 블록 독립성과 정규성 가정에 조건부이며 같은 머신의 시간 상관이 남는다. 불확실하면 미확정으로 기록한다. 후보 코드와 수치 기준은 확인 실행 전에 고정하고 중간 값을 보고 표본 수를 늘리거나 문턱을 바꾸지 않는다.

기능 제거 변형은 채택하지 않는다. 제품 후보는 원본 frost,정보 표시 시점·접힘·팝오버,동적 변경,빠른 전환,키보드·초점,여러 컴포저와 정리를 별도 검증해야 한다. 정보 표시를 뒤로 미뤄 DOM proxy만 낮추지 않았는지도 확인한다. 제품 테스트·타입 검사와 같은 제품 코드의 desktop·phone 검수 데모가 필요하며 사용자의 화면 판정은 별도다.

## 한도 종료 시점의 판정과 재개 순서

기능을 보존한 후보가 전환 지연의 추가분을 절반 이하로 줄였다는 근거는 얻지 못했다. 제품 변경에는 C1의 Workflow 스타일 수명 관리만 포함했다. C1의 테스트 694개·타입 검사·빌드와 합성 desktop·phone 데모 QA는 통과했지만, 설치된 원본 번들을 교체하지 않았다. 실제 BB 통합과 사용자의 화면 판정은 남아 있다. 다른 실험 변형은 제품 변경에 넣지 않았다.

다음 작업은 부팅 조회의 공개 계약과 부작용 분류를 먼저 완성하는 것이다. 실제 업데이트 상태를 조회하지 못하면 고정 응답의 적용 범위를 수집 전에 선언해야 한다. 이번처럼 수집을 시작한 뒤 누락된 경로를 하나씩 추가하는 반복은 피한다. 안전 검사를 낮추거나 실패 결과를 덮어쓰는 방식으로 수집을 통과시키지 않는다.

그다음 검증된 스타일시트의 비점수 선택자 통계를 한 번 확보해 작은 CSS 적용 범위 후보를 고른다. 현재는 이 통계가 없으므로 특정 규칙이 비싸다는 결론을 내리지 않는다. 비동기 표식 방식은 확인된 동기 동작 차이가 있어 우선 채택하지 않는다. controller 간 쓰기 뒤 읽기 가능성도 실제 순서를 먼저 관찰해야 하며, LoAF의 진입 위치만으로 getter가 원인이라고 정하지 않는다.

기능 보존과 탐색 근거를 충족한 후보에 한해 새로운 원본·프런트엔드 제외 조건을 함께 비교한다. 미사용 8블록 확인은 그 이후 단계이며 현재 실행하지 않았다. 같은 연구 대상을 반복한 결과를 독립 콘텐츠 검증으로 부르지 않는다. 자체 컴포저 교체는 공개 API와 구현 범위를 조사한 대안으로 남기며, 측정 없이 성능 개선 방법으로 채택하지 않는다.

재개용 읽기 경계 초안은 기존 설치 작업 목록 GET 한 개를 추가한 별도 자료로 보존했다. 실행기는 시작 단계에서 차단되며, 작은 오프라인 검사와 변경 범위 검토만 마쳤다. 실제 실행기 통합·전체 검증·새 슬롯은 준비되지 않았다. 첫 차수에서는 한도 종료 뒤 추가 실험이나 하위 작업을 시작하지 않았으며, 이번의 명시적 재개와 구분한다.
